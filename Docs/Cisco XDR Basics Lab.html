1. The six concepts you need

ConceptPlain meaning
WorkflowA flowchart that does a job: start, steps, end.
VariableA named box holding a value. Inputs come in, outputs go out, locals are scratch space.
ActivityOne step in the flowchart (set a variable, make a request, make a decision).
TargetA saved connection to a system you call, with its credentials.
IntentThe kind of workflow you pick when creating it. It decides where it can be used.
PlaybookA checklist for responding to an incident, where tasks can be manual or run a workflow.

Also useful: an observable is an IP, domain, hash and so on; a pivot menu is the right-click menu on one; an automation rule starts a workflow automatically; the worklog records what ran.

2. Setup (once)

  1. Log in to your Cisco XDR tenant (use the region URL you were given).
  2. Open Automate in the left navigation. Find the Workspace page and the Workflows list. Look around; nothing needs creating yet.
  3. Create an API client (needed for Lab 2): Administration > API Clients > add a client with read scopes for enrich and incidents. Copy the client id and password immediately and store them in environment variables, not in files.
  4. Install Python 3 and the requests library: pip install requests.
  5. Know your region: US, EU or APJC. It changes the API host names.

3. Lab 1: low-code workflow

Goal: build "Hello XDR", a workflow that takes a name and an IP, decides whether the IP is private, and returns a message. No external system, so nothing can break except your logic.

Variables

NameTypeKindExample
namestringinputAsha
ipstringinput10.1.2.3
is_privatebooleanlocaltrue
messagestringoutputHello Asha, 10.1.2.3 is a private address

Build steps

  1. Automate > Workflows > create new workflow. Name it Hello XDR. Choose a general intent (not tied to incidents) and write a description.
  2. Add the four variables above. Mark name and ip as inputs, message as an output.
  3. Add a Set Variable activity: is_private = whether ip starts with 10., 192.168. or 172.16. through 172.31.. In the expression editor use a "starts with" or regex-match condition (check which your editor offers). Simplest version: a Condition activity with three "starts with" checks joined by OR.
  4. On the true branch add Set Variable: message = Hello {{name}}, {{ip}} is a private address.
  5. On the false branch set message = Hello {{name}}, {{ip}} is a public address.
  6. Connect both branches to the end. Use the variable picker to insert {{name}} style references rather than typing them.
  7. Validate the workflow and fix any red errors (usually an unconnected branch or an empty field).
  8. Run it with test values and open the execution view. Click each activity and read its inputs and outputs; this is the single best way to learn.
  9. Run again with 8.8.8.8 and confirm the false branch.

Level 2: add a real lookup

Extend the workflow to ask XDR itself for the IP's verdict. Create a new workflow IP Verdict with ip as input and an HTTP request activity that POSTs to the Enrich deliberate endpoint (path below, check against the API explorer) with body [{"type":"ip","value":"{{ip}}"}]. This request needs a target pointing at the XDR platform host and an authentication method using your API client; if your tenant offers a built-in XDR target or a token atomic action, use that. Then pull the verdict from the response using the editor's path or JSON-extract option and output it as verdict.

4. Lab 2: the same thing through the API

Goal: do the verdict lookup from code, so you see what the workflow's HTTP activity does behind the scenes.

StepWhat happens
1Exchange client id and password for a bearer token.
2Send the IP to the Enrich deliberate endpoint with that token.
3Read the verdict from the response.
import os, json, requests

REGION = os.environ.get("XDR_REGION", "us")   # us | eu | apjc
HOST = {"us": "visibility.amp.cisco.com",
        "eu": "visibility.eu.amp.cisco.com",
        "apjc": "visibility.apjc.amp.cisco.com"}[REGION]

# 1. token (check the Authentication page for the exact path in your region)
TOKEN_URL = f"https://{HOST}/iroh/oauth2/token"
resp = requests.post(TOKEN_URL,
        auth=(os.environ["XDR_ID"], os.environ["XDR_PW"]),
        data={"grant_type": "client_credentials"})
resp.raise_for_status()
token = resp.json()["access_token"]
H = {"Authorization": f"Bearer {token}", "Content-Type": "application/json"}

# 2. verdict lookup (check the path in the API explorer)
URL = f"https://{HOST}/iroh/iroh-enrich/deliberate/observables"
body = [{"type": "ip", "value": "8.8.8.8"}]
r = requests.post(URL, headers=H, json=body)
print("HTTP", r.status_code)

# 3. read result
print(json.dumps(r.json(), indent=2)[:1500])

How to run it

export XDR_ID="client-xxxx"
export XDR_PW="your-password"
export XDR_REGION="us"
python verdict.py

Reading the result

  • 200 means success; the JSON lists verdicts by module (source) with a disposition such as clean, suspicious or malicious.
  • 401 means the token is wrong or expired, or the region host is wrong.
  • 403 means your API client lacks the enrich scope.

Running workflows by API

The Automation API (https://automate.us.security.cisco.com/api/, or the eu/apjc equivalents) manages automation objects and runs workflows. I do not have its exact endpoints verified, so open the Automation section of the interactive API documentation on developer.cisco.com, find the "list workflows" and "run workflow" operations, and try them with the same bearer token. Start with the list call: it is read-only and proves the token has automation access. Then run Hello XDR with {"name":"Asha","ip":"10.1.2.3"} as input.

Comparison: the workflow in Lab 1 is the same sequence as this script, with the editor hiding the token and JSON handling. When something fails in the editor, reproduce it here to see the raw response.

5. Lab 3: a basic playbook

Goal: a three-task playbook that you can run against any incident, using Lab 1's workflow.

PhaseTaskType
TriageRead the incident summary and note the main assetManual
TriageRun Hello XDR (or a verdict workflow) on an IP from the incidentWorkflow
CloseWrite a one-line conclusion and close the incidentManual
  1. Workflows used by a playbook must be of a type playbooks can run. If Hello XDR does not appear in the task picker, create a copy with the Incident Response intent, since that intent is designed for playbook tasks (check how your tenant labels it).
  2. Create a new playbook under Automate (the playbook area), name it Learning playbook.
  3. Add the phases and tasks from the table. Write clear instructions on the manual ones.
  4. Set it so it does not auto-apply to everything: give it a narrow rule, or leave rules empty and assign it manually (check what your tenant allows).
  5. Open a low-risk incident, assign the playbook, and step through the tasks.
  6. Afterwards open the incident's worklog and confirm the workflow run is listed.

6. Verification checklist

  1. I can log in and find Automate, Workflows and the playbook area.
  2. I created an API client and stored the secret safely.
  3. My script prints a token response and a verdict (or I understand the error code).
  4. Hello XDR validates and returns the right message for private and public IPs.
  5. I read the execution view for each activity.
  6. The playbook completes on a test incident and the worklog shows the run.

7. What to learn next

  • Loops: run a lookup for every observable in an incident.
  • Pivot-menu workflows: right-click an observable and run your workflow.
  • An automation rule to start a workflow when an incident is created.
  • A real target such as email or a ticketing system, using account keys.
  • Error branches and approvals before any risky action.
