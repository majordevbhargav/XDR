1. The big picture

Cisco XDR collects telemetry from integrations, correlates it into incidents, and lets you respond. Automation is the engine that turns analyst steps into repeatable, low-code workflows. Everything in the console is backed by REST APIs, so anything you can click you can usually script.

Integrations (data)→Detections→Incident→Automation rule / playbook→Workflow→Target (CrowdStrike, ServiceNow, email...)→Worklog

Workflows can be started in several ways: by an automation rule, by a playbook task, from an observable's pivot menu, by a webhook, by a schedule, manually, or through the API.

2. Glossary

TermMeaning
IncidentA group of correlated events with a priority score, affected assets, observables and a timeline.
ObservableAn indicator such as an IP, domain, URL, file hash, email or hostname. Observables get verdicts (clean, suspicious, malicious) and appear in pivot menus.
Verdict / dispositionThe reputation of an observable from sources like Talos and third-party feeds.
Pivot menuThe context menu on an observable. Response and lookup workflows can be added to it.
WorkflowA visual flow of activities and logic that does a job. Can call other workflows (child workflows).
ActivityOne step in a workflow: an API request, a condition, a loop, a variable change, an approval, a wait, and so on.
Atomic actionA prebuilt single-purpose action for a product (for example one call to an endpoint tool). Used as a building block.
TargetA saved definition of a system a workflow talks to (host, protocol, authentication). Integrations often create their own targets automatically.
Account keyA stored credential (username/password, token, key) referenced by a target so secrets stay out of workflow logic.
VariableA named value: workflow input, output, or local. Can be marked required or secure.
IntentThe workflow type chosen at creation, which decides where it can be used (incident response, observable pivot, general).
Automation ruleA trigger definition: conditions plus the workflows to run. A workflow only auto-runs if it is validated and attached to a rule.
WebhookA URL that accepts incoming data from an outside tool and can be wired to a rule to start workflows.
ScheduleA time-based trigger for recurring workflows (reports, cleanup, polling).
PlaybookA structured incident-response procedure: phases and tasks, each manual or backed by a workflow. A default playbook applies when none match.
CasebookA saved collection of observables and notes for an investigation (see section 7).
WorklogThe record of what was done on an incident, including workflow runs and links to them.
Exchange / XDR ConnectCisco's catalog of ready-made workflows, atomic actions and integrations you can install or learn from.
CTIMCisco Threat Intelligence Model: the common data model for threat information, regardless of source.
IROHThe name of the underlying platform API family (inspect, enrich, response, private intel).

3. The Automation Workspace

The Workspace is your home inside Automation. It shows your own workflows and atomic actions, recently run workflows, and favorites. From the All Workflows view you create, import and organize workflows. Each workflow has a summary (description, categories, variables, triggers, targets). Installed-from-Exchange items offer Uninstall; your own show Delete. The documented tenant limit is 500 workflows.

Use it for: finding and favoriting your frequently used workflows, checking recent runs, importing a colleague's exported workflow, and browsing what Cisco ships by default.

4. Workflows in depth

Anatomy

Start→Inputs / variables→Activities and logic→Outputs→End (success / failure)

Common building blocks

  • Requests: HTTP calls to any REST API through a target. This is where your API skills pay off.
  • Logic: conditions (if/else), loops over lists (for example each observable), parallel branches.
  • Data handling: set variables, parse JSON, extract fields with path expressions, build strings and bodies.
  • Human steps: approvals and notifications, so a person confirms risky actions.
  • Sub-workflows: reuse a tested workflow inside bigger ones.
  • Waits and retries: pause for asynchronous results, then check again.

Intents

IntentUse it when
Incident ResponseThe workflow works on an incident. It can be used by playbook tasks and can be triggered by an incident automation rule.
Observable actionAn analyst should run it from an observable's pivot menu. Once validated it appears wherever matching observable types do.
General / otherUtilities, scheduled jobs, webhook handlers, sub-workflows.

Lifecycle

  1. Create (choose intent) and define variables.
  2. Build activities, select targets.
  3. Validate. Auto-triggering and pivot menu placement only work after validation.
  4. Run manually with test data, inspect each step's inputs and outputs in the execution view.
  5. Attach to a rule or playbook task.
  6. Monitor through the Worklog and recent runs; export or import to move between tenants.

When you export a workflow, its associated automation rules go with it, so check the rule type before sharing.

5. Triggers: rules, webhooks, schedules

TriggerStarts whenExample

Webhook setup order: create the webhook (Automate > Triggers), create an automation rule using it, associate one or more workflows, and make sure the workflow contains an activity that handles the incoming payload.

6. Playbooks

A playbook documents and drives the response process. Typical phases: triage, contain, eradicate, recover, close. Each task can be manual (instructions for the analyst) or backed by a workflow. Playbooks have their own rules that decide which incidents they apply to; incidents that match none get the default playbook. Cisco ships a managed playbook, and you can create custom ones and share them between teams (a Playbook API exists for this). The AI assistant can use playbooks too, according to Cisco's blog.

7. Casebooks and "workbook" ideas

A casebook is a lightweight investigation container: you collect observables, add notes, and pivot from them. Use casebooks for hunting and ad hoc work, and incidents plus playbooks for formal response. If someone asks for a "workbook", clarify whether they mean a casebook (investigation notes), the Workspace page (automation home), or a playbook (response procedure). I believe casebooks are also reachable through the API; confirm the paths in the API docs.

Services and base URLs (US region)

EU and APJC regions use their own hostnames (for example visibility.eu.amp.cisco.com, automate.eu.security.cisco.com, automate.apjc.security.cisco.com). Match your tenant's region or you get authentication errors.

Authentication

  1. Administration > API Clients (administrator only) and create a client. Pick scopes carefully (read versus write; for example enrich, response, private-intel, incident and automation scopes).
  2. Client credentials grant: send client id and password to the token endpoint, receive a short-lived JWT bearer token.
  3. Call APIs with Authorization: Bearer <token>. Request a new token when it expires.

The other client type, OAuth Authorization Code, is for apps that ask other users to trust them and need a website to host.

Typical API tasks

Exact endpoint paths and payloads vary; use the interactive explorer on developer.cisco.com/docs/cisco-xdr, which includes read-only demo credentials.

9. Worked examples

Python: get a token and enrich an IP 
import requests
TOKEN_URL = "https://visibility.amp.cisco.com/iroh/oauth2/token"  # confirm for your region
tok = requests.post(TOKEN_URL, auth=(CLIENT_ID, CLIENT_PW),
                    data={"grant_type": "client_credentials"}).json()["access_token"]
H = {"Authorization": f"Bearer {tok}", "Content-Type": "application/json"}

url = "https://visibility.amp.cisco.com/iroh/iroh-enrich/deliberate/observables"  # verify path
r = requests.post(url, headers=H, json=[{"type": "ip", "value": "8.8.8.8"}])
print(r.json())
Workflow pattern: enrich every observable in an incident
  1. Input: incident id. Request: fetch the incident and its observables.
  2. Loop over observables.
  3. Inside the loop: request verdict; condition on "malicious".
  4. Collect malicious ones into a list variable.
  5. If the list is not empty: add a note to the incident and branch to approval, then containment.
Workflow pattern: webhook to incident
  1. Create webhook and rule; copy URL into the external tool.
  2. Workflow reads the payload and extracts key fields.
  3. Build an incident object (title, description, observables, severity).
  4. POST it through the Private Intel API, then notify a chat channel.
Workflow pattern: safe containment
  1. Look up the asset; stop if unknown.
  2. Check an allowlist of critical hosts; require senior approval for those.
  3. Approve, isolate, verify status, write to worklog.
  4. Provide a reverse workflow to un-isolate.

10. Best practices

  • Keep credentials in account keys; mark variables secure.
  • Build small workflows and compose them with sub-workflows.
  • Always write results back to the incident so the worklog is complete.
  • Add error branches; a silent failure is worse than a loud one.
  • Add approvals for destructive actions and allowlists for critical assets.
  • Use least-privilege API clients; one client per integration or script.
  • Name consistently (for example SN - Create ticket) and use descriptions and categories.
  • Test with synthetic incidents first; rules can fire in bulk against real ones.
  • Be idempotent: check whether a ticket or block already exists before creating one.
  • Respect API rate limits; add waits and paging in loops.

11. Troubleshooting

SymptomLikely cause and fix
401 UnauthorizedExpired token, wrong client secret, or wrong region host. Re-request the token.
403 ForbiddenAPI client lacks the scope. Edit scopes or create a new client.
Workflow never starts from a ruleWorkflow not validated, not attached to the rule, or the rule conditions never match. Test with a loose condition.
Not in the pivot menuWrong intent or observable type, or not validated.
Target errorsWrong account key, certificate or network path from the cloud to the product, or missing integration license.
Empty variable valuesWrong JSON path. Inspect the raw response in the execution view and fix the extraction.
Integration action missingIntegration not enabled, or the licensing tier does not include it.
