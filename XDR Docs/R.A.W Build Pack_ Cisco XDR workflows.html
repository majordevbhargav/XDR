R.A.W Build Pack

Blueprints for the four Response/Automation/Workflow rows in the HCL sheet: Create Ticket, Complete Containment, Create a Trigger, Create a Custom Playbook. Three workflows plus one rule and one playbook.

PrerequisitesWF1 TicketWF2 ContainWF3 TriggerPlaybookPre-flight scriptEvidence
Read first. These are blueprints, not importable files: Cisco's export format is not something I can reliably hand-write. Activity names and field labels in the editor vary by version, so I describe each step by what it does. Where an out-of-the-box atomic action exists for CrowdStrike or ServiceNow in your tenant, prefer it over the raw HTTP request shown here. Use placeholders like {{incident.id}} to mean "insert the variable with the editor's picker".

1. WF1: Create Ticket (ServiceNow)

Sheet row: Create TicketIntent: Incident ResponseName: SN - Create ticket from incidentOutcome: AR

Variables

NameTypeSource
incident_idstring, inputSupplied by the incident context
incident_title, priority_score, incident_urlstring, localRead from the incident (title and score fields)
ticket_number, ticket_sys_idstring, outputServiceNow response
snow_urgencystring, localMapped from score (below)

Steps

#ActivityConfiguration
1Get incident detailsUse the incident-context input or an atomic action that returns title, priority score, link. Store in local variables.
2Map urgencyCondition on score: >= 800 sets 1, >= 500 sets 2, else 3. Adjust thresholds with the customer.
3Duplicate check (idempotency)GET /api/now/table/incident?sysparm_query=correlation_id={{incident_id}}&sysparm_limit=1&sysparm_fields=number,sys_id. If result has an item, set the outputs from it, skip to step 6.
4Create ticketPOST /api/now/table/incident via the ServiceNow target. Headers: Content-Type: application/json, Accept: application/json. Body below.
5Parse responseOn HTTP 201: result.number to ticket_number, result.sys_id to ticket_sys_id. Otherwise go to the error branch.
6Write back to XDRAdd a note or worklog entry to the incident: "ServiceNow ticket {{ticket_number}} created." (Use the add-incident-note action available in your tenant.)
7Error branchOn failure, add a note with the HTTP status and message, then end as failed. Optionally email the SOC.
{
  "short_description": "XDR incident: {{incident_title}}",
  "description": "Priority score: {{priority_score}}\nXDR link: {{incident_url}}",
  "urgency": "{{snow_urgency}}",
  "impact": "2",
  "category": "Security",
  "correlation_id": "{{incident_id}}"
}

Test: run on a test incident; confirm a ticket appears in ServiceNow with the right fields; run again and confirm no second ticket is created; break the credentials and confirm the failure note appears.

2. WF2: Complete Containment (isolate endpoint, block hash)

Sheet row: Complete Containment WorkflowIntents: Observable action (host) and Observable action (file hash)Outcome: AR

Build two small pivot-menu workflows plus a reverse one. The sheet's examples (isolate endpoint, block domain/URL, block hash) are "e.g.", so host isolation and hash blocking are enough to pass; add domain blocking only if an enforcement integration (for example a DNS security product) is connected.

2a. Isolate host: CS - Isolate host

#ActivityConfiguration
1Inputhostname (the observable value), requested_by.
2Find deviceCrowdStrike atomic action, or GET /devices/queries/devices/v1?filter=hostname:'{{hostname}}'. Take resources[0] as device_id. If empty, add note "host not found" and end.
3Safety checkCondition: hostname in a protected list (domain controllers, core servers) means require approval from a senior role; else standard approval.
4ApprovalApproval activity to the analyst or lead: "Isolate {{hostname}}?" with a timeout. Declined or timed out ends with a note.
5IsolatePOST /devices/entities/devices-actions/v2?action_name=contain with body {"ids":["{{device_id}}"]}.
6VerifyWait 30 to 60 seconds, then GET /devices/entities/devices/v2?ids={{device_id}} and check status is contained (or the containing state). Retry a few times.
7RecordAdd note to the incident: who approved, device id, result.

2b. Block hash: CS - Block file hash

#ActivityConfiguration
1Inputsha256. Condition: reject if the value is not 64 hex characters.
2Check verdict (optional)Look up the hash verdict; warn if it is clean before blocking.
3ApprovalSame pattern as 2a.
4Create IOCPOST /iocs/entities/indicators/v1 with an indicator of type sha256, action prevent, applied_globally: true, and a description naming the incident. Check CrowdStrike's current body format.
5RecordAdd note to the incident.

2c. Undo: CS - Lift containment

Same lookup, then POST to the same devices-actions endpoint with action_name=lift_containment. You need this to reset your lab host after each test.

CrowdStrike base URL depends on your cloud (for example api.crowdstrike.com or a regional one). If the XDR integration already provides atomic actions, those handle authentication for you and the raw paths above are only for reference.

Test: right-click the lab host in the incident graph, run Isolate, approve, confirm it loses network access in the Falcon console, run Lift, confirm it returns. Repeat for a harmless test hash (for example the EICAR file hash).

3. WF3: Create a Trigger (priority score rule)

Sheet row: Create a TriggerObject: automation rule + notification workflowOutcome: AR

3a. Notification workflow: Notify - High priority incident

  1. Intent: Incident Response. Read title, score, link, top assets.
  2. Send the message: email (or Webex/Slack if connected) with subject "High priority XDR incident: {{incident_title}} (score {{priority_score}})" and the link in the body.
  3. Optionally call WF1 as a sub-workflow so one rule gives notification and ticket.
  4. Add a note to the incident that the notification was sent. Validate.

3b. The rule

SettingValue
LocationAutomate > Triggers > Automation Rules
Rule typeIncident rule
ConditionPriority score greater than 800 (answers the sheet's "Priority Score ??" note; confirm the scale in your tenant)
ActionRun Notify - High priority incident (and WF1 if not nested)

Test: first set the threshold low (for example 100) so existing incidents trigger it, confirm the email arrives and the worklog records a run, then raise it to 800 and note which incident exceeds it. Remember the workflow must be validated or the rule will not run it.

5. Pre-flight script (Python)

Run this before building, to prove credentials and network paths work. Fill the placeholders; keep secrets in environment variables.

import os, requests

# ---- ServiceNow ----
SN = os.environ["SN_URL"]            # https://dev12345.service-now.com
SN_AUTH = (os.environ["SN_USER"], os.environ["SN_PASS"])
H = {"Content-Type": "application/json", "Accept": "application/json"}

r = requests.post(f"{SN}/api/now/table/incident", auth=SN_AUTH, headers=H,
    json={"short_description": "XDR preflight test", "correlation_id": "preflight-001"})
print("SN create:", r.status_code, r.json().get("result", {}).get("number"))

q = requests.get(f"{SN}/api/now/table/incident", auth=SN_AUTH, headers=H,
    params={"sysparm_query": "correlation_id=preflight-001", "sysparm_limit": 1})
print("SN dup-check found:", len(q.json().get("result", [])))

# ---- CrowdStrike ----
CS = os.environ.get("CS_BASE", "https://api.crowdstrike.com")
t = requests.post(f"{CS}/oauth2/token", data={
    "client_id": os.environ["CS_ID"], "client_secret": os.environ["CS_SECRET"]})
tok = t.json()["access_token"]
CH = {"Authorization": f"Bearer {tok}"}
host = os.environ["CS_TEST_HOST"]
d = requests.get(f"{CS}/devices/queries/devices/v1", headers=CH,
                 params={"filter": f"hostname:'{host}'"})
print("CS device ids:", d.json().get("resources"))

# ---- Cisco XDR token ----
x = requests.post(os.environ["XDR_TOKEN_URL"],
    auth=(os.environ["XDR_ID"], os.environ["XDR_PW"]),
    data={"grant_type": "client_credentials"})
print("XDR token:", x.status_code)

This script only reads from CrowdStrike and creates one test ticket (delete it afterwards). It does not isolate anything.
