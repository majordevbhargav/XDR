Cisco XDR POV Guide

A plain-language walkthrough of the HCL Tech NDR/XDR requirements sheet, followed by a hands-on guide to building workflows in your own XDR tenant.

1. How to read the sheet 2. Integration 3. Platform 4. Response / Automation 5. Incident Management 6. AI 7. Build guide 8. API testing 9. Test plan
Note on menu names. Cisco renames UI items between releases. Where this guide names a menu (for example Automate > Workflows), treat it as the right neighborhood and confirm the exact label in your tenant. Where I am less sure of a detail I say so.

1. How to read the sheet

This is a POV (Proof of Value) checklist: a customer, HCL Tech, defines what Cisco XDR must demonstrate during a trial. Each row is one test. You fill in Level of Importance with the customer, then mark Requirement Met? and add notes after demonstrating it.

ColumnMeaning
CategoryGroup the row belongs to: Integration, Platform, R.A.W, I.M, A.I.
POV Functional RequirementThe capability being tested.
DescriptionWhat exactly must be shown. The Description column sometimes carries a hint (for example "Pull CrowdStrike agent inputs").
Level of Importance0 = N/A in this environment, 1 = not important, 2 = nice to have, 3 = need to see, 4 = must see. Prioritize 4s and 3s.
Requirement Met?Pass or fail, filled after testing.
NotesCurrently holds the owner names (for example Mohit Gupta, Vikas Jain), who are responsible for each integration on the customer side.
Business OutcomeWhy it matters. DS Detect Sooner, PI Prioritize by Impact, SI Speed up Investigation, AR Accelerate Response. Nearly every row maps to one or more; the goal of the POV is to prove these four outcomes.

2. Integration

XDR is only as good as the data it receives. These rows connect data sources and enrichment so later detections have something to work with. All integration rows target all four outcomes (DS, PI, SI, AR).

RequirementWhat it meansHow to demonstrate
Endpoint: CrowdStrike via APIXDR connects to CrowdStrike with API credentials, so it can ingest detections and also run actions (isolate host, contain hash) from XDR.Show CrowdStrike detections appearing in XDR incidents, then run a containment action on a test host.
NVMNetwork Visibility Module, part of Cisco Secure Client. It reports flow records from each endpoint including process name, hash, user and device. This is how "which process made this connection" is answered.Deploy to a test laptop, generate traffic, show process-level connection data.

Network devices export it to a collector (typically Cisco Secure Network Analytics), which feeds XDR. It builds the behavior baseline and finds lateral movement.Enable export on devices, confirm the collector sees flows, show an incident that uses them.
SPAN from EPGA SPAN (port mirror) copies actual packets from a critical application's Endpoint Group in Cisco ACI to a sensor, giving deeper visibility than NetFlow for the most important apps.Mirror one critical app, show the extra detail in the sensor.

These rows check what the XDR console itself can do once data is flowing: displaying, prioritizing and detecting.

Detection use cases

Each of these needs a test you can run to generate the alert. Your goal is to trigger the behavior safely in a lab and show the resulting incident.

RequirementWhat it detectsSuggested test
Lateral MovementAn attacker or tool moving from machine to machine (server to server, client to server) using admin protocols such as SMB, RDP or WinRM.From a test host, connect to several internal servers in a short period using an approved account.
Behaviour BaselineXDR learns normal NetFlow and SPAN patterns, then alerts when something deviates (new talker, traffic spike). Needs days of learning data, so start early.Let the baseline build, then create unusual volume or a new destination.
Abnormal UserA user acting unlike their normal pattern, detected by combining NVM and ISE identity.Log in as a test user from an unusual device or at an unusual time.
Malicious Process DetectedA running process whose hash matches a known malicious list. Hint: data comes from the CrowdStrike agent.Use an EICAR test file or other safe test sample in the lab. Never real malware.
Potential System Process ImpersonationA process named like a system process (for example svchost.exe) running from the wrong place. Hint: rename a file and execute it.Copy a harmless executable, rename it to a system process name, run it.
PowerShell RDP ConnectionPowerShell making connections on the RDP port (3389), suggesting scripted remote access. Source: NVM or CrowdStrike.Use PowerShell to open a TCP connection to port 3389 on a lab host.
Connection to TOR IPTraffic to the TOR network, often used for command-and-control or evasion.In a lab, connect to a known TOR relay address.
Port 8888 from multiple sourcesSeveral devices sending files to one internal host on an unusual port, which can mean data staging or exfiltration.Run a simple listener on 8888 and send small files from a few lab machines.

Do these tests only in the customer-approved POV lab and tell their SOC beforehand so real alarms are not raised.

7. Build guide: your first workflows

Vocabulary

  • Workflow: a visual flow of steps (activities) with logic. Maximum 500 per tenant.
  • Atomic action: one prebuilt step, such as one CrowdStrike call.
  • Target: a saved connection to a system (host, auth).
  • Account key: a stored credential used by a target. Never hard-code secrets in a workflow.
  • Variable: an input or output value; can be set as required, secure or local.
  • Intent: chosen at creation. Incident Response workflows can be used by playbook tasks or incident rules; observable-based workflows show up in pivot menus.
  • Automation rule: the trigger that runs a workflow on a condition, webhook or schedule.

Workflow A: create a ServiceNow ticket from an incident

  1. Prepare ServiceNow. Get a developer instance, or the customer's test instance, and a service account that can create records in the incident table.
  2. Create the account key and target. In Automate, add an account key with the ServiceNow credentials, then a target pointing to your-instance.service-now.com using it (basic or OAuth, as your instance allows). If an out-of-the-box ServiceNow integration or exchange workflow exists, install it instead and learn from it.
  3. Create the workflow. Automate > Workflows > New. Choose the Incident Response intent so it can receive an incident. Name it clearly, for example SN - Create ticket from incident.
  4. Add the inputs. The incident context arrives through the workflow's incident input. Define the variables you need (title, priority, id, observables) if the intent does not supply them.
  5. Add the ServiceNow call. Use an HTTP request activity (or the ServiceNow atomic action) with method POST to /api/now/table/incident. Body example: 
    {
  "short_description": "XDR: <incident title>",
  "description": "Priority score: <score>\nXDR link: <incident url>",
  "urgency": "1",
  "caller_id": "xdr.service"
}
  6. Read the response. Extract result.number (for example INC0010023) into a variable.
  7. Write back to XDR. Add a step that adds a note or worklog entry to the incident with the ticket number, so the Worklog review passes.
  8. Add error handling. On a non-2xx response, write a failure note to the incident rather than silently ending.
  9. Validate and run. Use the validate option, then run against a test incident. Open the execution view to see each step's inputs and outputs, and fix mappings as needed.
  10. Check the Worklog to confirm the run is listed with a link.

Workflow B: contain an endpoint (with approval)

  1. Confirm the CrowdStrike integration is enabled (Administration > Integrations); it should provide a target and atomic actions.
  2. Create a workflow with an observable intent for device or hostname type, so it appears in the node-graph pivot menu.
  3. First step: look up the host in CrowdStrike and get its device id. Stop with a clear message if not found.
  4. Add an approval step (email or in-console) asking an analyst to confirm. This is the "human in the loop" customers expect; if approval is declined, end and log it.
  5. Call the CrowdStrike contain (network isolate) action with that device id.
  6. Poll or check the host status, then write the outcome to the incident note.
  7. Create the matching reverse workflow (lift containment) so you can reset the lab host.
  8. Repeat the pattern for file-hash and domain blocking using the relevant integration actions.

Workflow C: trigger on high priority

  1. Open Automate > Triggers > Automation Rules and create an incident rule.
  2. Set the condition on priority score (for example above 800) and, optionally, on a tactic or asset tag.
  3. Attach Workflow A (or an email-notification workflow). The workflow must be validated, or the rule will not run it.
  4. Generate a test incident above the threshold and confirm the workflow starts on its own.
  5. Webhook variant: create a webhook trigger to get a URL, point an external tool at it (the Meraki example in Cisco's docs follows this pattern), and map the incoming payload to workflow variables.

Playbook: tie it together

  1. Create a new playbook in the Automate area; give it rules for which incidents it applies to. If no playbook matches, the default one is used.
  2. Add phases and tasks, for example Triage (enrich observables), Contain (Workflow B), Notify (Workflow A), Close.
  3. For each task, choose to run a workflow or leave a manual step with instructions.
  4. Assign, test on an incident, and confirm each task completes and the worklog shows the activity.

8. API testing

Use API calls to test outside the UI, to script setup, and to inspect results. Create an API client under Administration > API Clients (an administrator is needed).

ServiceUS base URL
Platform (Inspect, Enrich, Response)https://visibility.amp.cisco.com/iroh/
Private Intel (creating incidents)https://private.intel.amp.cisco.com/ctia/
Automationhttps://automate.us.security.cisco.com/api/
Incidents and Investigationshttps://conure.us.security.cisco.com/v2/

EU and APJC use region-specific hosts. The flow is always: request a token with client id and password, then send Authorization: Bearer <token>.

import requests
TOKEN_URL = "https://visibility.amp.cisco.com/iroh/oauth2/token"  # confirm on Cisco's Authentication page
tok = requests.post(TOKEN_URL, auth=(CLIENT_ID, CLIENT_PW),
                    data={"grant_type": "client_credentials"}).json()["access_token"]
H = {"Authorization": f"Bearer {tok}"}

# Search incidents
r = requests.get("https://conure.us.security.cisco.com/v2/incident/search/count", headers=H)
print(r.status_code, r.text)

A community MCP server for Cisco XDR also exists (listing, getting and updating incidents, and listing and running workflows), if you want to drive the tenant from an AI assistant. Treat it as unofficial and keep credentials in environment variables.

Common problems: 401 means an expired or wrong-region token; 403 means the API client lacks the scope; a workflow that never fires means the rule's workflow is not validated; a target that fails usually means a wrong account key or blocked network path.

9. Suggested POV test plan

  1. Agree importance levels with the customer; focus on the 4s and 3s first.
  2. Get integrations working first (CrowdStrike, ISE, NVM, NetFlow), because detections depend on them.
  3. Start the behavior baseline early so it has learning time.
  4. Run the safe detection tests and record the incident for each.
  5. Build Workflows A, B and C, then the playbook.
  6. Walk one incident from detection to closure and review the worklog.
  7. Fill in Requirement Met? and Notes for every row with evidence (screenshot, incident id).

Left out to keep this guide compact: per-integration setup screens, full API payloads for every endpoint, and CrowdStrike or ServiceNow-specific field lists. Ask for whichever you want next.
