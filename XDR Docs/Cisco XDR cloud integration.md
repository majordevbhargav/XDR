# Wiring AWS, Azure and GCP into Cisco XDR

All three clouds can feed Cisco XDR Advantage, but only two of them do it natively, and none gives you cloud response actions out of the box. **AWS and GCP have dedicated XDR integration pages that state they require the Advantage tier**, so your tenant qualifies ([AWS](https://docs.xdr.security.cisco.com/Content/Integrations/amazon-web-services-integration.htm), [GCP](https://docs.xdr.security.cisco.com/Content/Integrations/google-cloud-platform-integration.htm)). **Azure has no dedicated XDR page.** Cisco lists it as a telemetry source "configured in Secure Cloud Analytics" (SCA), the former Stealthwatch Cloud, now folded into XDR ([XDR Integrations](https://docs.xdr.security.cisco.com/Content/Administration/integrations.htm)). In every case you grant Cisco read-only access to network flow logs (who talked to whom) and, for AWS and GCP, audit logs (who did what through the cloud API). Cisco's analytics build behavioral baselines from those logs and raise detections that XDR correlates with endpoint, identity and network data into prioritized incidents. The main caveats are these. The SCA-to-XDR migration is actively in flight (Cisco's GCP cutover dates run through **24 October 2026**). APJC support is listed but not tested. Azure's flow-log type is changing. XDR's capability table lists **no response actions** for AWS or GCP, so containment needs custom workflows. For an automation engineer new to cloud, the practical route is a throwaway lab account per cloud, read-only integration roles, sample or simulated attacks, and automations that notify and enrich before they ever contain.

## Why cloud telemetry is a different kind of evidence

Cloud is rented infrastructure driven by APIs, and the provider only secures "the cloud itself". Customers keep responsibility for data, identities and configuration in every service model. AWS and Microsoft each state this split ([AWS](https://aws.amazon.com/compliance/shared-responsibility-model/), [Microsoft](https://learn.microsoft.com/en-us/azure/security/fundamentals/shared-responsibility)). The consequence for a security engineer is that the control plane (console, API, IAM) becomes the perimeter, and every configuration change is an auditable API call. There is also no tap or SPAN port on a provider's network, so visibility depends on logs the provider generates, and many of those are opt-in and regional. Our notes' own (unverified, general-knowledge) framing adds that cloud assets are ephemeral, which breaks IP-based asset tracking.

Attackers exploit exactly that gap. In Google's Cloud Threat Horizons data, **weak or absent credentials accounted for 47.1% of initial access and misconfiguration for 29.4%**, with exploits a small minority (Google's own customer base, so possibly unrepresentative) ([Google Cloud Threat Horizons H2 2025](https://cloud.google.com/security/report/resources/cloud-threat-horizons-report-h2-2025)). The same report describes actors who stole session cookies despite MFA, and who disabled then re-enabled MFA on an admin account to hide activity. MITRE's Cloud matrix gives names to the patterns: Cloud Accounts abuse (T1078.004), Unsecured Credentials (T1552), Resource Hijacking, i.e. crypto-mining (T1496) and Transfer Data to Cloud Account (T1537) ([MITRE ATT&CK Cloud Matrix](https://attack.mitre.org/matrices/enterprise/cloud/)).

Two telemetry families do most of the work. Audit logs record control-plane actions: CloudTrail management events cover things like AttachRolePolicy and StartLogging, while the data-plane events (S3 object reads, Lambda invocations) are high volume and **not logged by default** ([AWS CloudTrail](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference.html)). Flow logs record IP traffic to and from network interfaces, collected out of band with no throughput impact ([AWS VPC Flow Logs](https://docs.aws.amazon.com/vpc/latest/userguide/flow-logs.html)). Flow logs show that something talked and how much, but not which identity did it. Audit logs show which identity acted, but not what the network did. You need both, and an XDR is where they meet other products' data.

That is the case for XDR rather than reading cloud logs in isolation. Our notes' illustrative scenarios (composed by the researcher, not Cisco case studies) show the pattern: an infostealer on a developer laptop followed by use of the laptop's AWS keys from a hosting-provider IP looks like a harmless API call without the endpoint join. Mining shows up as RunInstances in an unused region plus outbound flows to pool addresses, each low-signal alone. Cisco's documentation supports the mechanism: incidents are groups of correlated events matched on shared indicators (devices, IPs, hostnames, usernames, file hashes) and mapped to MITRE ATT&CK, with a **0 to 1000 priority score** combining detection risk and asset value ([Incidents](https://docs.xdr.security.cisco.com/Content/Incidents/incidents.htm)). Whether cloud assets receive an asset value is undocumented, so treat that as an assumption.

## How Cisco XDR consumes cloud data, and what is changing under you

XDR's detections page names four native telemetry categories (network, cloud, identity, endpoint), with cloud and identity coming from Secure Cloud Analytics ([Detections](https://docs.xdr.security.cisco.com/Content/Incidents/detections.htm)). SCA was end-of-sale 13 November 2023 with its capabilities moving into XDR ([Cisco SCA support page](https://www.cisco.com/c/en/us/support/docs/security/stealthwatch-cloud/218040-configure-sca-to-ingest-multiple-aws-acc.html)). The result is two coexisting configuration paths: legacy SCA-portal setup, and native modules under Administration > Integrations > Third-Party. Only Administrators can add integrations, a health check runs on add, and My Integrations shows Connected or Error ([XDR Integrations](https://docs.xdr.security.cisco.com/Content/Administration/integrations.htm)).

The transition is dated and close. Cisco's transition notice says GCP flow logs appear in XDR Activities from 16 September 2026 and audit logs from 30 September, GCP audit-log detections cut over on **7 October**, NetFlow on 21 October, and **the SCA UX becomes unavailable on 24 October 2026**. Detections change names, logic and evidence rather than mapping one-for-one, SCA webhooks must be rebuilt as XDR workflows, and integration endpoints may change, so firewall allowlists need review ([SCA transition](https://www.cisco.com/c/en/us/support/docs/security/secure-cloud-analytics/226312-transition-from-secure-cloud-analytics.pdf)). We found no equivalent Azure statement, which is the largest open risk for Azure onboarding (see below). The AWS page also states that integrations migrated from SCA keep their flow and CloudTrail ingestion, with the ExternalId set to the SCA tenant ID ([AWS](https://docs.xdr.security.cisco.com/Content/Integrations/amazon-web-services-integration.htm)).

Licensing and region are straightforward on paper. Threat-intelligence and ITSM integrations sit in Essentials; other third-party integrations need Advantage or Premier, and the tier shows on the My Account page ([XDR Integrations](https://docs.xdr.security.cisco.com/Content/Administration/integrations.htm)). XDR lists regions as North America, Europe and Asia Pacific/Japan/China, with **15 published XDR source IPs for APJC** to allowlist if your cloud-side storage or APIs are IP-restricted (same source). The SCA and GCP marketplace pages list the same three regions ([Connect: GCP](https://connect.xdr.security.cisco.com/integration/google-cloud-platform)). **Unverified:** we found no APJC-specific cloud limits or data-residency statements, and the SCA marketplace page says "Contact sales" for its license. The Oct 2025 data sheet gives 90-day default retention (180 or 365 purchasable) and a 2 GB per user per month default ingestion quota, but does not confirm that the quota applies to cloud logs ([XDR data sheet](https://www.cisco.com/c/en/us/products/collateral/security/xdr/xdr-ds.pdf)).

## What each cloud requires

| | AWS | Azure | GCP |
|---|---|---|---|
| Where configured | Native XDR AWS module (SCA portal path also documented) | SCA only; no XDR Azure page | Native XDR module, Administration > Integrations > Third-Party |
| Network data | VPC Flow Logs to S3 | NSG or virtual network flow logs to Blob storage | VPC Flow Logs via Cloud Logging or Pub/Sub |
| Control-plane data | CloudTrail management events in S3 | Entra ID audit logs (Graph); Activity Log removed from guide | Cloud Audit Logs via Pub/Sub |
| Credential model | Cross-account IAM role, external ID | Entra app registration with client secret | Service account JSON key |
| Cisco-documented IAM | Read-only policy JSON from portal | Monitoring Reader, Storage Blob Data Reader, Graph AuditLog.Read.All | Not published |

### AWS: a cross-account role and two S3 paths

The XDR AWS page requires Advantage and ingests VPC flow logs and CloudTrail management events (read and write), supports multiple accounts through IAM Role ARNs and STS, and supports KMS-encrypted buckets. It asks for a custom flow-log format including all version 2 attributes (version 3 recommended, without `reject-reason`), and for `pkt-srcaddr` and `pkt-dstaddr` so NAT-gateway traffic stays visible ([AWS](https://docs.xdr.security.cisco.com/Content/Integrations/amazon-web-services-integration.htm)). The older Quick Start (v3.5, Cisco index date 20 December 2024, so menu paths may differ) gives the mechanics. You create flow logs to an S3 bucket, create a policy from JSON the portal supplies (named `swc_policy`), and create a role trusting **Cisco account 757972810156** with a required external ID equal to your portal subdomain. You then paste the role ARN under Credentials, add the bucket under VPC Flow Logs, apply a generated bucket policy to the role, and register the CloudTrail S3 path ([AWS Quick Start](https://www.cisco.com/c/dam/en/us/td/docs/security/stealthwatch/cloud/configuration/AWS_Quick_Start_Guide_DV_3_5.pdf)). Success shows as an `AWS: <bucket>` sensor and a Permissions page matching expectations. Expect flows roughly 10 minutes after delivery starts and up to 24 hours for entity data (same source).

Three points matter operationally. Cisco's example policy uses wildcards and `Resource: "*"` in places and tells you to narrow it for production; deleting the `CloudCompliance` statement drops posture checks as a least-privilege lever ([multi-account TechNote](https://bxin.cisco.com/c/en/us/support/docs/security/stealthwatch-cloud/218040-configure-sca-to-ingest-multiple-aws-acc.pdf)). Multi-account setups point each account's flow logs at one bucket and add one role per account. We found **no official CloudFormation or Terraform template** and no AWS Organizations-wide onboarding, so scripting per account is your job. Finally, GuardDuty is not needed for flow-log or CloudTrail detection. It is a separate Advantage-tier module that returns indicators and sightings for investigation only ([GuardDuty](https://docs.xdr.security.cisco.com/Content/Integrations/amazon-guardduty-integration.htm)).

### Azure: one app, three read roles, a storage account

Cisco's current guide (v6.0, 6 November 2025) is the only Azure guide, and it reads NSG or virtual network flow logs from Blob storage plus an Entra ID app for context. You (the human, with Owner or equivalent per subscription) create an app registration named `xdra-reader` and a client secret, grant Graph `AuditLog.Read.All` with admin consent, and assign **Monitoring Reader** on each subscription and **Storage Blob Data Reader** on each flow-log storage account. You then create a storage account in the same region as the monitored resources, register the `microsoft.insights` provider per subscription, enable Network Watcher and flow logs, and enter the Entra URL, application ID and secret in SCA under Settings > Integrations > Azure ([Azure Quick Start v6.0](https://www.cisco.com/c/dam/en/us/td/docs/security/stealthwatch/cloud/configuration/Microsoft_Azure_Integration_Quick_Start_Guide_DV_6_0.pdf)). Storage accounts should appear within about 10 minutes. The setup-time heavy roles can be removed afterwards (inference). Calendar a secret-rotation reminder; that expiry stops ingestion is the researcher's inference, not Cisco's statement.

On the NSG-versus-virtual-network question, Microsoft says **NSG flow logs retire on 30 September 2027** and that creating new ones is no longer supported; it recommends virtual network flow logs ([Microsoft](https://learn.microsoft.com/en-us/azure/network-watcher/nsg-flow-logs-overview)). Cisco's v6.0 guide offers both types, so **new onboarding should use virtual network flow logs**, with standard (not premium) storage in the VNet's region, and should not run both log types on the same resources ([Microsoft: VNet flow logs](https://learn.microsoft.com/en-us/azure/network-watcher/vnet-flow-logs-overview)). **Unverified:** the date Microsoft blocked new NSG logs (the researcher recalls 30 June 2025 but could not confirm), whether the date has since been extended, whether SCA picks up VNet-format blobs without change, and the Asia-Pacific region table for VNet flow logs. The Azure data path also depends on SCA, whose UX Cisco says disappears on 24 October 2026; we found no document saying how Azure is configured after that, so ask Cisco before building anything Azure-specific. Do not confuse this with the separate Microsoft Cloud integration (Defender for Endpoint, Defender for Office 365, Sentinel) or the Entra ID automation integration, which use their own credentials ([Microsoft Cloud](https://connect.xdr.security.cisco.com/integration/microsoft-cloud), [Entra ID](https://docs.xdr.security.cisco.com/Content/Integrations/microsoft-entra-id-integration.htm)).

### GCP: service account, flow logs and two Pub/Sub pipelines

The GCP page is the most hands-on. You enable VPC Flow Logs per subnet with **secondary sampling set to 100%** (Cisco says the default is 50%), enable the Cloud Logging API (required) and Cloud Monitoring API (recommended, used for the "GCP Cloud Function Invocation Spike" alert), create a service account, and upload its JSON key under Administration > Integrations > Third-Party > Google Cloud Platform. For high volume you route flow logs through a Log Router sink to topic `vpc_flows-topic` with pull subscription `swc_subscription` (2-hour retention, 600-second ack deadline). Audit logs use a separate topic, subscription and sink (`swc-watchlist-*`) created with gcloud, plus a publisher grant to the sink's writer identity ([GCP](https://docs.xdr.security.cisco.com/Content/Integrations/google-cloud-platform-integration.htm)). Copy the names exactly; Cisco mixes underscores and hyphens. You verify under Investigate > Activities with source "Google VPC Flow Logs", and the Credentials page shows per-project monitoring status. Changing the key later requires a new module.

**Cisco publishes no IAM role names for the service account.** Candidate roles in our notes (logging viewer, Pub/Sub subscriber on the two subscriptions, compute viewer, monitoring viewer, project listing) are the researcher's suggestions from Google documentation and need Cisco TAC confirmation. Data Access audit logs are off by default and can be costly to enable ([Google](https://docs.cloud.google.com/logging/docs/audit/configure-data-access)), so audit detections may initially see only Admin Activity events. Another inference to check in Logs Explorer: Cisco's sink filter targets the newer `networkmanagement.googleapis.com/vpc_flows` log, which may not match flow logs enabled the legacy way. Organization-level onboarding and APJC specifics are not documented.

## What the engineer gets, and what to automate first

XDR gives you detections with MITRE mapping, incident correlation and asset context, plus workflows. Workflows can be triggered from the pivot menu, incident playbooks, automation rules, API, a Run button or email rules, with limits of 500 workflows, 200 actions per workflow, a 30-minute run time and an API rate of 20 per minute for Start and Webhook ([Workflows](https://docs.xdr.security.cisco.com/Content/Automate/workflows.htm)). SCA's built-in actions are read-oriented (get alerts, observations, flows by IP, roles by IP, device details) plus watchlist domain management ([Connect: SCA](https://connect.xdr.security.cisco.com/integration/secure-cloud-analytics)). Cisco's capability table lists **AWS, GuardDuty and GCP with no response actions**, while Entra ID, Duo, Umbrella and Defender for Endpoint offer controls and responses ([Capabilities](https://docs.xdr.security.cisco.com/Content/Administration/cisco-third-party-integrations-and-capabilities.htm)). Cloud containment such as deactivating an access key therefore means workflows calling the cloud's own APIs; that is an inference, and no prebuilt cloud workflows were verified.

Our notes' design guidance (general practice, unverified against Cisco docs) sorts automation by blast radius. Notify, ticket, enrich and annotate are safe to automate freely. Disabling an identity-provider user, deactivating (not deleting) an access key, quarantining a tagged non-production instance or snapshotting a disk deserve approval or narrow conditions. Terminating instances (it destroys evidence), bulk IAM edits, broad IP or region blocks and revoking credentials that production services share need a human. Use a separate, least-privilege automation identity with explicit denies on destructive actions, reversible steps, allowlists for crown-jewel accounts and logging of every action. The integration identities themselves stay read-only.

Set expectations on timing and noise. Flow logs arrive in minutes, behavioral alerts need a baseline (the AWS partner blog claims over 80% of alerts within 14 days; the Detection Settings page shows "baseline days" per detection), and detections default to not opening incidents until you enable "Always create incident" ([AWS APN Blog](https://aws.amazon.com/blogs/apn/cloud-posture-and-threat-analytics-with-cisco-secure-cloud-analytics), [Detection Settings](https://docs.xdr.security.cisco.com/Content/Administration/detection-settings.htm)). This is detection and investigation, not inline prevention.

## A safe, cheap learning path

Start with one brand-new personal sandbox per cloud and never test in employer, customer or shared accounts. Set MFA, avoid long-lived admin keys, and create a low-threshold budget alert before any workload (budgets alert rather than reliably stop spending, per general knowledge). Free offers change, so re-read each sign-up page. AWS's free plan (from July 2025) offers up to **$200 in credits** and expires at six months or when credits run out ([AWS](https://aws.amazon.com/about-aws/whats-new/2025/07/aws-free-tier-credits-month-free-plan/)). Google offers **$300 credit** plus always-free products ([Google](https://cloud.google.com/free)). Azure's page advertises $200 for 30 days, but the page body did not restate it and the move to pay-as-you-go makes charges possible ([Azure](https://azure.microsoft.com/en-us/pricing/free-services/)). Whether a card is required is unverified, and we did not open Cisco's AWS trial link (https://www.cisco.com/go/aws-trial), so ask Cisco about a lab entitlement.

The cheap pattern is one small VM, one bucket, one network with flow logs and a short lifecycle (1 to 7 days) and management-event audit logging only. Costs to watch are concrete. GCP VPC flow-log generation is **$0.25/GiB** at the first tier, Cloud Logging ingestion is $0.50/GiB after 50 GiB free, and Pub/Sub is $40/TiB after 10 GiB free ([VPC](https://cloud.google.com/vpc/network-pricing), [Logging](https://cloud.google.com/stackdriver/pricing), [Pub/Sub](https://cloud.google.com/pubsub/pricing)). Azure bills flow-log collection per GB with 5 GB/month free per subscription, and Traffic Analytics, which Cisco does not need, has no free tier ([Microsoft](https://learn.microsoft.com/en-us/azure/network-watcher/nsg-flow-logs-overview)). Cisco's 100% sampling advice trades cost for fidelity; start on key subnets. AWS cost figures are unverified, though S3 lifecycle deletion of noncurrent versions after one day is Cisco's own advice.

For attack practice, AWS GuardDuty can generate labeled sample findings with no real activity, and AWS recommends an isolated account for simulations ([AWS](https://docs.aws.amazon.com/guardduty/latest/ug/sample_findings.html)). Stratus Red Team detonates ATT&CK-mapped techniques against live AWS, Azure, Entra ID, GCP and Kubernetes accounts, for example `stratus detonate aws.defense-evasion.cloudtrail-stop`, but its warnings and cleanup guidance were not reviewed, so read each technique and run cleanup ([Stratus](https://stratus-red-team.cloud/)). Do not run real miners or scan third parties. Suggested order for the engineer: GCP first (native module, explicit steps, verification in Activities), AWS second, Azure last, because its path depends on the SCA migration. Check provider penetration-testing policies, which we did not fetch.

## Conclusion

The sharpest finding is that "integrating a cloud with XDR" is currently three different projects at three maturity levels. GCP is a native module with a dated cutover, AWS is native with SCA-era mechanics underneath, and Azure is an SCA configuration whose post-24 October home is undocumented. The most useful early step is therefore a short written confirmation from Cisco covering the APJC tenant's cloud path, the Azure post-migration procedure, GCP's least-privilege roles and any AWS infrastructure-as-code templates, rather than building around guesses.

For the engineer, the main benefit is not the cloud alert itself but the join between cloud evidence and identity and endpoint context. The main trap is the gap between detection and action. XDR will tell you a key was misused, but containment is yours to build, and the safe habit is to automate read-only enrichment first and reserve irreversible actions for humans until a lab has proven the workflow.
